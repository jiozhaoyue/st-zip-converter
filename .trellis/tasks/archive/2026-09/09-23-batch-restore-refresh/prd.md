# 批量恢复编排与单次刷新引导

## Goal

在公开契约允许的范围内，把“多选导入 → 逐个恢复 → 一次刷新”做成可观察、可断点续跑、失败明确的批量编排；若宿主缺少分段上传/原子合并契约，则如实降级为“逐卷导入 + 完成后引导刷新”，绝不伪造原子性。

## Background

- 工作区已支持多选 ZIP 入库（`file-drop.js`），恢复入口 `restoreToHost()` 每次只接收一个完整 ZIP（`FormData` → `/api/users/restore`）。
- `splitter.js` 的每个分卷都是合法独立 ZIP，天然适合“逐卷导入”而非“字节拼接还原”。
- 宿主未提供公开的分段上传/合并恢复端点（OQ 待证）；Authority 的 transfer/blob 属于扩展隔离数据面，不能直接写入酒馆用户目录。
- 刷新行为受 L1-MR-4/L1-MR-5 约束：只能用宿主公开 UI/API，不能 hook 内部逻辑。

## Requirements

- 设计批量恢复编排状态机：队列 → 逐项恢复（merge/overwrite 按用户选择）→ 失败项记录原因并可单独重跑 → 全部完成后给出刷新引导。
- 与现有 TaskManager 断点语义衔接：恢复任务可中止；中断后能从失败/未完成项继续，不要求从头再来。
- UI 必须如实展示非原子性：逐卷恢复期间部分数据已生效；全部完成前不提示“已合并完成”。
- 刷新引导：全部成功后，若宿主无公开刷新 API，则展示明确的“请刷新页面/重新打开会话”引导，而不是自动 `location.reload()` 强刷（避免打断宿主进行中的工作）。
- 对超过单包限制的场景，复用 `splitter.js` 分卷结果按序恢复；超大单文件独占卷需单独提示。
- Authority 不可用时全功能可用（本地编排即可）；Authority 可用时仅作可选的进度持久化增强。

## Acceptance Criteria

- [ ] 研究结论落盘：宿主是否存在公开的分段上传/合并恢复接口与刷新 API（research/ 目录，附证据）。
- [ ] 编排状态机与失败重跑语义成文，含中止/续跑路径。
- [ ] UI 文案明确区分“逐卷恢复中（非原子）”与“全部完成”。
- [ ] 刷新引导不依赖宿主内部实现；无公开 API 时为显式用户操作引导。
- [ ] Authority 降级路径（无后端时本地编排照常工作）有测试计划。

## Out of Scope

- 不实现服务端合并恢复（除非宿主公开契约被证实存在）。
- 不自动强制刷新宿主页面，不 hook 宿主路由/事件。

## Open Questions

- OQ-1：Luker/ST 是否有公开的批量/分段恢复或刷新端点（须以官方文档为准）。
- OQ-2：逐卷恢复的默认模式是 merge 还是由用户逐次选择。
- OQ-3：全部完成后是否提供“立即刷新”按钮（`location.reload()`）还是仅文案引导——涉及打断宿主的风险取舍，需用户拍板。
