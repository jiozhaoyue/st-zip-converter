## D0 「实时同步」的准确释义（先把口径钉住）

用户裁决 U-2 的原文是「**只有实例在运行时同步**，然后**通过插件产生数据包**，然后同步，
中间同步可能通过脚本，**至少数据产生靠插件**」。据此：

| 不是 | 而是 |
| --- | --- |
| 常驻 watcher / 守护进程 | **按需触发**：实例在跑时才同步；实例不在跑时无事可做 |
| 纯前端一键跨实例推送 | 插件在**源实例内**产包 → **脚本**搬运灌入各目标（纯前端无法跨实例写入：同源限制） |
| 复用宿主原生 `/api/users/backup` 产包 | **由插件 UI 在页面内产包**（本轮的实质改动） |

⇒ **「实时」= 需要时即可跑一次，且每次跑的是当前数据**，而非后台持续推送。
这与 U-2 的「只有实例在运行时同步」是同一件事的两种说法。

### D1.2 产包器契约

新增 `scripts/instance-sync/produce-via-plugin.cjs`（**入库**，U-11）：

```
node scripts/instance-sync/produce-via-plugin.cjs \
  --source real-luker          \   # 必填，无默认值（见 D1.3 纪律）
  --layout  st|tt|l|native     \   # 目标布局（一步直出，见 D2）
  --out     <目录>             \   # 产物落点
  --timeout <ms>               \
  [--categories characters,chats,lorebooks,...]   # 默认全类目
  [--include-backups]                              # 默认**不含** backups/（沿上一轮 U-4）
```

内部流程（每一步都是**有界等待**，L1-MR-7）：

1. `getInstance(--source)` ⇒ URL / profile / 目录；**打印解析出的端口**（可审计）；
2. 起持久化 context（`instances.cjs` 的 `PROFILES`）→ 打开源实例页面；
3. **R-20 前置自检**：读实例里插件的版本（`git -C <插件目录> rev-parse --short HEAD`），
   与工作区 HEAD 比对；**不一致即拒绝执行**并提示先 `git pull`
   —— 这是把 R-20 的纪律**程序化**（上一轮是靠人记）；
4. 按 `openWorkbench()` 打开工作台（**判可见用 `getBoundingClientRect`，不用 `offsetParent`**，spec §11.1）；
5. 设类目勾选（`#category-checkboxes`）、关掉 `includeBackups`；设目标（`#target-select`）；
6. **等计划条就绪**（`#plan-summary-bar` / `#output-estimate-text` 出现非零估值）后点「宿主拉取」；
7. 等产物入待导出区（`.eq-title` 计数增加 / `files` store 的 `origin='host-export'` 增量）；
8. 点该条目的「下载」→ **捕获 `download` 事件** → `saveAs(--out)`；
9. 产出**读数 JSON**（`条目数 / 压缩后体积 / sha256 / 源实例版本 / 插件版本`）落 `research/`。

### D1.3 端口纪律：**产包器不走 E2E 守卫，但继承守卫的三条精神**

**冲突**（必须显式解决）：产物源是 **Real Luker（`:8004`）**，而 `e2e/lib/guard.cjs` 的白名单
是 `{8001, 8003, 8899}` ⇒ **产包器若走守卫会被自己拦下**。

**解法（不修改守卫、不放宽 E2E）**：

- 产包器**不调用** `e2e/lib/guard.cjs` —— 它**不是 E2E**，是数据同步工具；
- 但它**必须**继承守卫的三条精神（`guard.cjs` 的四条纪律中除「Real 拒绝」外的三条）：

| 继承 | 实现 |
| --- | --- |
| **启动时断言**，失败即非零退出 | `--source` 必填且必须在登记表内，否则立即退出 |
| **不给默认值** | **没有** `?? 'dev-luker'` 这类兜底（兜底值就是误连入口） |
| **禁止自动改写目标** | 不得因「端口被占」回退到别的实例（改端口 = 换数据区） |
| 另加 | 拒绝 `8000`（L0-16）；**打印解析出的端口与 side**（Dev/Real）供人工核对 |

**为什么这样切是干净的**：登记表（`instances.cjs`）是**所有**实例的唯一定义点，
守卫只是**E2E 的**使用限制。产包器是另一个消费者，各有各的使用限制 —— 不是两份端口表。

### D1.4 为什么把 R-20 做进产包器

上一轮的 R-20 教训是：**E2E 验证的是实例里装的插件版本，不是工作区代码**，
当时靠人记住。产包器比 E2E **更**需要这条 —— 因为「数据产生靠插件」意味着插件的版本
**直接决定产物正确性**。故把它做成**硬门禁**（D1.2 第 3 步），而不是提醒。

## D2 OQ-2 实测：插件能否**一步直出**目标布局

**要验的推论**：插件的宿主拉取可「直接指定目标酒馆格式」（README 特性 1）⇒
若成立，一次产包即得目标布局包，**省掉 `build-packs.cjs` 的二次转换**，减少口径漂移面。

**实测方案**（阶段 1，只读）：

1. 对**同一个**源，分别以 `--layout st` / `--layout tt` / `--layout l` 产三次包；
2. 与上一轮 `build-packs.cjs` 产出的同名布局包做**条目级比对**（复用 `lib/t1-coverage.cjs`）：
   条目路径集合、条目数、每条 `crc32`；
3. **判定**：
   - **成立**（条目级一致或差异可解释）⇒ 生产链简化为「插件三布局包一步产出」，
     `build-packs.cjs` 退为**交叉核对装置**（不删）；
   - **不成立** ⇒ **给出实测理由**（差异清单 + 归因），沿用 `build-packs.cjs`，
     并把这个结论写进 spec（避免下次再试一遍）。

**读数落 `research/one-step-layout-<layout>.json`。**

### D4.1 三道守卫**必须**在写入前生效

1. **链接守卫**（`lib/link-guard.cjs`）：解析数据路径下的 symlink / junction，
   指向工作区仓的**默认跳过**，重跑须显式 `--allow-links` —— 这是 `P-19` 的防护，
   上一轮实测有 **1090 条**穿透写进 `My-repo/ST-BgLoader`。
2. **只读快照**（`snapshot-manifest.cjs`）：写入前对每个目标落
   `research/pre-<target>-<ts>.json`（相对路径 + 大小 + mtime）。
3. **宿主源码禁改**（**新 `L0-1` 的硬约束**）：写入前断言所有目标路径都落在
   「被宿主仓 `.gitignore` 覆盖」的范围内（判据 `git check-ignore`）；
   **任何一条落在源码面 ⇒ 立即中止**。这是把新规则**程序化**，不是靠自觉。

### D4.2 ST 的 settings 教训（上一轮 J 事故，**不得回归**）

`import-st.cjs` 的 settings 分支必须是**按目标键集的交集合并** ——

3. **归一后的系列计数**（上一轮 165 = 165）。

## D6 可重跑性（AC-A2 / AC-P4 的证据设计）

**同一源连续两次产包，条目数与体积一致** —— 但要小心一个陷阱：

- **陷阱**：两次产包若间隔期间源实例的**数据变了**（用户在用），条目数当然不同 ⇒
  这不是「不可重跑」，是「源变了」。
- **设计**：两次产包**连续执行**，并在读数里**同时记录源的 mtime 快照**
  （`data/default-user` 下文件的相对路径 + mtime 的哈希）。若两次快照一致而产物不一致 ⇒ 真缺陷；
  若快照不一致 ⇒ 读数**标注为「源在期间变动」**，不算失败，并重跑。

**这一条不写清楚，AC-A2 会变成一个假红或假绿。**

## D7 风险与回滚

| 风险 | 缓解 | 回滚 |
| --- | --- | --- |
| **写穿链接污染工作区源码仓**（`P-19`，已实际发生 1090 条） | `link-guard.cjs` 默认跳过 + `D4.1` 第 3 条的源码面断言 | **不可撤回**；只能事前拦截 ⇒ 故两道守卫都必须在写入前跑 |
| **ST settings 膨胀搞停宿主**（上一轮 J 事故） | 交集合并（`D4.2`）+ 体积异常断言 | `test-results/settings-repair-backups/` 留底（上一轮的）；本轮写入前快照可定位 |
| **Dev ST / Real ST 无备份**（U-3 风险接受） | `merge` 语义 + 只读快照 + 零删除核对 | **无回滚能力**（登记为已知接受风险） |
| **插件版本与工作区不一致 ⇒ 产物不可解释**（R-20） | `D1.4` 的硬门禁 | 先 `git pull` 更新实例再跑 |
| **PT 是「尽力而为」存储**（浏览器未授予持久化；磁盘不足时可能**不通知就清空**） | `import-pt.cjs` 对 >100 MB 默认拒绝（须 `--allow-large`） | 源仍在各磁盘实例，可重灌 |
| **一键直出（D2）不成立** | 回退 `build-packs.cjs`（既有、已验证） | 无（只是少一条优化） |

**改动面预估**：新增 `scripts/instance-sync/produce-via-plugin.cjs`（+ 可能的 `lib/` 小件）
与 E2E 产包 spec；**复用既有全部搬运脚本，不改其语义**；`src/**` **零改动**
（本子任务只消费插件能力，不改插件）。

### D7.1 与子任务 B 的顺序关系（**依赖必须写清，不靠树位置暗示**）

- **无硬依赖**：A 用的插件的**宿主拉取**能力已存在且未被 B 触碰（B 只动转换路径的续传）。
- **但有一条纪律**：B 若改了插件代码 ⇒ 按 R-20，跑 A 的产包**前**必须把源实例的插件更新到
  工作区版本。`D1.2` 第 3 步的硬门禁会**自动拦住**这种情况 ⇒ 顺序上**先做 B 更省事**
  （一次实例更新覆盖两者），但**先做 A 也成立**（只是可能要更新两次）。
- 父任务 `prd.md` 的 AC-P1（B）与 AC-P2（A）**无先后约束**。
